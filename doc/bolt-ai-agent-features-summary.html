Bolt Project Summary

AI Agent Features in Bolt

Bolt is evolving from a human-operated execution backend into an agent-facing runtime that can execute a plan, explain what happened in machine-readable form, package the run for replay, and accept targeted plan patches instead of full resubmission.

Source: `doc/ai-ready-execution-engine.md`
Demo: `scripts/bolt_agent_demo.py`
Real adapter: `bolt/tool/AgentRuntimeExecutor.cpp`
API: `demo/agent_runtime_api/server.py`

What the feature set is trying to solve

The core problem is that AI agents need a tighter runtime contract than a human does. A person can read logs, infer root causes, and retry by hand. An agent needs structured outputs that are stable, explicit, and easy to act on programmatically.

  • Deterministic execution requests for upstream planning agents
  • Structured critique for downstream tuning and diagnosis agents
  • Replay capsules for reproducibility and auditability
  • Patch-oriented retries for fast, incremental refinement

Why Bolt is a good base

The design leans on capabilities Bolt already has: portable plan representation, rich operator support, trace capture, Python extensibility, and multi-runtime experience.

The agent work is therefore mostly about adding a thin semantic layer over execution rather than inventing a separate planner or chatbot wrapper.

1. Core Agent-Native Capabilities

Execution Critique

After a run, Bolt emits structured operator findings instead of forcing the caller to reverse-engineer logs. The critique is shaped for machine action: dominant operators, evidence, symptoms, and suggested next actions.

  • Identifies hot operators and failure symptoms
  • Separates local operator findings from global findings
  • Generates recommended next actions for an optimizer agent
  • Encodes evidence such as memory, rows, wall time, and shuffle
{
  "symptom": "high_peak_memory",
  "operator_type": "HashAggregation",
  "suggested_actions": [
    "increase_partition_count",
    "rewrite_to_two_phase_aggregation",
    "enable_spill"
  ]
}

Replay Capsule

The capsule is the reproducibility primitive. It bundles the plan, split metadata, query config, connector properties, critique, and trace summary so another agent can replay or compare the same run.

  • Preserves the execution context in one object
  • Supports debugging, auditing, and regression triage
  • Can redact or mask sensitive connector values
  • Acts as the base object for future patches
{
  "capsule_version": 1,
  "query_id": "clickbench_q7_demo",
  "query_config": { "task.max-drivers-per-task": "8" },
  "trace_summary": [ ... ]
}

Patch-Oriented Execution

The design explicitly supports small plan edits. Instead of submitting an entirely new query, an agent can supply a patch against a base capsule. In the demo API, the narrow implemented patch is retune_aggregation; in the design doc, the broader target is subtree replacement and incremental plan refinement.

Capability What an agent gets back Why it matters
Structured critique Symptoms, evidence, dominant operators, next actions Lets an optimizer or debugger reason without reading logs
Replay capsule Plan, config, splits, trace summary, result snapshot Supports reproducible comparison and auditing
Patch loop Before/after rerun anchored to one capsule lineage Enables fast iterative optimization
Agent-native failure surface Category, retriable flag, affected node, suggested actions Improves autonomous recovery decisions
Design center: Bolt should be a runtime that agents can execute against, inspect, replay, patch, and improve.

2. What Is Already Implemented Today

Lightweight CLI Demo

The script scripts/bolt_agent_demo.py is a no-build, standard-library demo of the full run/replay/patch loop. It does not execute real Bolt operators, but it does model the agent-facing contract and generate realistic artifacts.

  • Command surface: run, replay, patch
  • Simulated operator metrics for scan, filter, project, aggregation, join, Python node, and exchange
  • Automatic critique generation from those metrics
  • Capsule emission with redacted connector properties

Operator-Aware Recommendations

The demo maps operator symptoms to actionable next steps. Examples in code include high-memory hash aggregation, low-selectivity scans, large join build sides, and Python nodes that block vectorization.

This is important because it turns raw telemetry into a control loop an AI system can actually use.

Current Limitation

The CLI demo is intentionally synthetic. It proves the interaction model and artifact shapes, but it is not a full Bolt execution path. That gap is partly addressed by the newer API demo backed by a real C++ executor.

Implemented today: a runnable concept demo with concrete metrics, artifacts, and patch effects.

3. Real Execution Adapter and HTTP API

C++ Executor

bolt/tool/AgentRuntimeExecutor.cpp moves the agent story beyond simulation. It accepts a JSON request, builds a real Bolt plan with PlanBuilder, executes it, enables trace capture, and returns result rows plus trace metadata.

  • Builds input vectors from inline schema and rows
  • Supports filter, project, aggregation, order by, and limit
  • Allows single or partial/final aggregation strategy
  • Captures per-node trace data through Bolt query tracing

Standalone HTTP API

demo/agent_runtime_api/server.py wraps the C++ executor with a simple local HTTP service. It persists run artifacts, indexes capsules, and exposes endpoints for execution, replay, patching, and artifact retrieval.

  • POST /runs
  • POST /replays
  • POST /patches
  • GET /runs/{run_id}
  • GET /capsules/{capsule_id}
  • GET /artifacts/{run_id}/{artifact_name}

The API is demo-oriented, but the execution path is already real Bolt, not just a toy simulation.

4. Bottom Line and Near-Term Roadmap

Bottom Line

Bolt already has a credible AI agent feature set centered on execution critique, replay capsules, and patch-based optimization. The repository shows both the design vision and an incremental path from simulated demo to real traced execution.

In practical terms, Bolt is becoming an execution substrate that optimizer, debugging, regression triage, and evaluation agents can reason about directly.

Best-Fit Agent Use Cases

  • Physical plan tuning agents
  • Replay-based debugging agents
  • Regression triage and benchmark agents
  • Autonomous data workflow controllers
  • Audit and postmortem assistants

What still looks most important next

  • Broaden the real adapter beyond the current narrow request subset
  • Enrich failure objects with explicit retryability and root-cause hints
  • Expand patch operations from aggregation retuning to general plan edits
  • Carry more trace and sampled input context into capsules when safe
  • Harden the API with production concerns such as auth and scheduling
